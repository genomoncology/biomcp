# Optimize: Command-level article spec runtime

## Scope Constraint

Ticket 505 is a measurement-only spike. It explicitly says not to implement or edit production/test code. There is also no separate exploit implementation: the experiment compares frozen revisions `36d964db4c066f638ae298df6e60b3ac315221c4` and `046814b919eab1bbe16b897342e6d3a3627244cb` with one now-removed shared binary.

Accordingly, this phase treats the frozen ticket-502 change as the one measured optimization pass, then evaluates two single-change hypotheses against retained profiles. Rejected hypotheses were stopped before code changes—the safe equivalent of reverting—rather than violating the ticket. Projected values below are clearly separated from benchmark results.

## Starting Baseline

Exact suite execution was not repeated because cleanup of the shared frozen binary and temporary worktrees was part of the ticket contract; running the current branch would not be the same comparison.

## Optimization Passes

### Pass 1 — Share the article fixture lifecycle

- **Profiled hotspot:** fixture setup/cleanup in article spec blocks and the standalone renderer. The baseline performs 24 lifecycle paths, estimated at 2976 ms total.
- **Measured cost and floor:** lifecycle overhead is under 1% of 335081 ms; its theoretical floor is zero.
- **Approach:** ticket 502's runner-owned shared fixture, already present in frozen candidate `046814b9`.
- **Before / after:** 335081 to 332983 inclusive, **0.63% faster**. Full routine changed 567221 to 707933, **24.81% slower**.
- **Correctness:** exact article/full pass-skip and command-exit parity.
- **Disposition:** retained for safe ownership and cleanup, but rejected as the performance winner. It is below the 5% convergence threshold and far below ticket 502's 60% target.

### Pass 2 — Bypass pacing for all loopback URLs

- **Profiled hotspot:** candidate `src/sources/rate_limit.rs:116-149`, where equal fixture prefixes reach longest-prefix policy selection and `sleep_until`. The later Semantic Scholar policy wins the equal-length tie and contributes a two-second interval.
- **Measured cost:** candidate median article command sum is 331473 ms, about 99.6% of wall time. Diagnostic duration follows the two-second connection staircase. Applying that staircase to grouped median command evidence attributes about 331078 of 331483 ms to pacing, leaving about 406 ms of command work.
- **Approach considered:** skip rate limiting whenever the destination is loopback.
- **Before / projected after:** 332983 inclusive to about 1916, **99.42% projected**. This is an upper-bound projection, not an after benchmark.
- **Disposition:** rejected before implementation. Users may deliberately use local proxies for live traffic, so this would compromise production rate-limit correctness. It also violates ticket 505's no-code constraint.

### Pass 3 — Consolidate repeated fulltext assertions

- **Profiled hotspot:** 11 executions of `get article 22663011 fulltext`, contributing 110176 ms, or 33.24% of grouped article command time.
- **Measured cost and floor:** removing ten executions gives an upper-bound saving of 100160 ms. The theoretical floor still includes one command and all other article behavior.
- **Approach considered:** execute the command once and share output across ten assertion blocks.
- **Before / projected after:** 332983 inclusive to 232823, **30.08% projected**. This is not an after benchmark.
- **Disposition:** rejected before implementation. It is a broad harness architecture change, may weaken independent Markdown behavior contracts, and is dominated by the narrower pacing fix. It also violates the ticket's no-spec-edit constraint.

## Convergence

The only measured implementation improved the primary metric by **0.63%**, below the flow's 5% convergence threshold. The required additional passes were evaluated but not implemented: one is unsafe for real local proxies and one is a broader, contract-risking harness rewrite. Three consecutive permissible code passes cannot exist under a ticket that expressly forbids code changes.

Optimization therefore stops at the measurement boundary, not because latency reached its theoretical minimum. The profile is decisive enough to route the next change: live-upstream pacing, rather than fixture lifecycle or rendering, consumes nearly all article time.

## Remaining Opportunities

1. **Recommended next build:** add an explicit fixture-only signal at the HTTP rate-limit layer. Skip live pacing only when that signal accompanies test-owned local source-base overrides. Preserve all real PubTator, PMC, Semantic Scholar, and API-key-dependent intervals. Benchmark the same cold article command set before/after with at least three repetitions.
2. **Contain fixture environment lifetime:** candidate article overrides remain active for later variant specs and explain much of the full-routine regression. Prove whether later commands should be fixture-backed, then scope or clear overrides without restoring repeated launches.
3. **Assertion execution reuse:** sharing command output could save process and request work, but only after defining a mechanism that preserves independent executable behavior contracts and failure visibility.
4. **Parallel execution:** potentially large but intentionally deferred. Shared fixture state, cold-storage transitions, caches, and process cleanup would need isolation contracts first.

The follow-up build must preserve resolver order; clean no-`--pdf` misses; XML, HTML, PDF, PMC OA, Figshare assets/siblings, cold-storage 202→200 retry, provenance/license, JSON, saved-file, and JATS Markdown behavior; runner cleanup and standalone renderer fallback; cache/XDG isolation; exact expected command exits; and the offline routine lane.
