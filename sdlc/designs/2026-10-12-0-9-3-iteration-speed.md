# BioMCP 0.9.3: faster building and testing

A read-only study of the BioMCP repository at commit `6f62f42cf` (main, 2026-10-12). It measures where build and test time goes, what the tests prove, and what to change in 0.9.3 so a ticket's edit-build-test loop gets short again. Every number below is either read from a file (path and line given), taken from a command and its output, or measured on the build host (a 4-core, 14 GB Linux machine with Rust 1.93.1) or in CI. Numbers I inferred rather than measured are marked "inferred".

## Summary

Findings:

1. BioMCP compiles one crate of 292,766 lines of Rust (`find src -name '*.rs' | xargs wc -l`), and 44% of those lines are test code (93,601 lines in test-only files plus 35,247 lines of inline `#[cfg(test)]` items in 268 production files, counted by a brace-matching scan of the source). Every edit recompiles the whole crate. On the build host, touching one file under `src/` costs 157 s for the dev test build and 253 s for the `spec` profile binary that the Python lane and the spec lane use (measured; the host's cargo config turns incremental compilation off; with it on, a warm rebuild of the test archive takes 67 to 144 s and a touch plus one targeted test group 55 s). Inside the crate the test code is the critical path: the lib test unit compiles in 157 s against 92 s for the lib.
2. An empty `build.rs` (`fn main() {}`) makes every file in the repository a build input. A build script that prints no `rerun-if-changed` line makes cargo rerun it whenever any file in the package changes, and cargo finds that out by scanning every file the package would publish. Cargo's own log shows the chain on the build host: the build script is dirty because a stray log file in the clone was newer than the last build (`PrecalculatedComponentsChanged`), then the lib is dirty because the build script changed, then the binary (measured, see the build table). So editing a spec page, a Python test, a workflow, a document, or `tools/rust-source-size-inventory.json` costs the same recompile as editing Rust: 157 s in the dev build and 253 s in the spec build, in every checkout and in CI. The script's two former jobs left in earlier tickets (`git log -- build.rs`); deleting the file ends the scan. Measured: with the script present, touching `spec/entity/gene.md` rebuilt the crate in 175 s; with the script deleted, touching a spec page, a Python test and `tools/rust-source-size-inventory.json` together cost 2.7 s and compiled nothing, while a touched Rust file still cost 156 s.
3. One ticket pays for the same code to be compiled in three codegen profiles plus a clippy check: the dev profile for `make test` (Makefile:36), the `spec` profile for the spec lane and the Python lane (Makefile:23, 43-45; Cargo.toml:156-163), and the release profile for `make verify` and CI's release-panic job (Makefile:112-113; ci.yml:225). On the build host a cold dev build takes 258 s, a cold nextest archive 265 s, and the spec-profile crate compile 253 s on every change (measured). Both routine lanes pass against the dev build's binary (measured, see Build), so the second profile buys nothing in routine work. CI's canonical-gates job spends 8.8 to 11.3 minutes in `make test` and 10.6 to 11.3 minutes in `make spec` on the same runner, back to back (Actions API, runs 38303133131 and 38300593102).
4. `make test` takes 635 s on the build host with nothing to compile, and the Python lane is 473 s of it; the 4,205 Rust tests run in 149 s (measured). The Python lane's floor is three files, because `pytest -n 4 --dist loadfile` sends every test of a file to one worker: one test that runs `cargo package` and a cold `cargo check` of the packaged crate in a fresh target directory (426 s, `tests/test_source_package_boundary.py:104-140`), one trial search test that takes 381 s for a single fixture-backed command (`tests/test_ctgov_trial_search_detail_reuse.py`) because the binary spends the time cleaning the developer's own HTTP cache at start-up (the same command takes 1.2 s once the cache index is in memory; see the Python paragraph under Test times), and the ratchet's self-tests (427 s across `tests/test_quality_ratchet_contract.py`, 175 s of it in one test that runs the whole ratchet over the repository). `make spec` takes 684 s and 675 s in two consecutive runs, with nothing to compile, nothing in the HTTP cache (the routine pages run with the cache off), and the machine mostly idle (the load average stayed near 0.2 through the second run).
5. CI runs eight jobs per push; a green run takes 22 to 28 minutes of wall time and about 70 runner-minutes. Five jobs compile Rust from separate caches. The release-panic job spends 16.4 minutes building a release binary to run one test (`ci.yml:223-226`). The repository produced 107 CI runs on 2026-10-11 and 85 on 2026-10-12 (`gh run list`), so the CI bill is on the order of 100 runner-hours a day during a release push (inferred from runs times minutes).
6. The test suite has 4,031 Rust unit tests inside `src/`, 228 Rust integration tests under `tests/`, 961 Python test functions (1,252 cases once parametrized), and 592 executable bash blocks across 52 spec pages (counts by grep, see Measurements). By file name, 786 of the 961 Python tests check the repository's own process: release workflows, records, documentation wording, and the checkers themselves; 175 drive the binary or the MCP server. Seven of the 26 Rust integration test binaries read source files and assert on their text (`tests/list_cli_structure.rs:8-45` and six siblings); they compile and link against the whole crate to do it.
7. The quality ratchets cost more than they catch. `tools/check-quality-ratchet.py` is 109 KB with more than twenty audits; `tools/dead-code-exceptions.json` lists 124 allowed dead items, 82 of them in `src/sources` and 80 with a reason that mentions "fixture"; `tools/rust-source-size-inventory.json` has been changed in 90 of the 676 commits since 2026-10-01, and 36 of those commits changed nothing but a `tools/*.json` file (git log). The source carries 123 `#[allow(dead_code)]` and 63 `#[allow(unused_imports)]` markers.
8. The HTTP cache is on by default. Every provider request goes through `http-cache-reqwest` with `CacheMode::Default`, a `max-stale=86400` request header, and a size-aware `cacache` store under `<cache root>/http` (`src/sources/mod.rs:1320-1350`, `src/cache/manager.rs:73-81, 238`). `BIOMCP_CACHE_MODE=infinite` serves stale entries without revalidation and `off` bypasses the store but not the start-up clean (`src/sources/mod.rs:563-571, 1226-1232`). A pre-baked cache for tests is possible but brittle: entries are `bincode`-serialized `HttpResponse` plus `CachePolicy` blobs keyed by `method:uri` under hashed index files, and the client's constructor physically deletes entries older than `max_age` (24 hours by default) every time it starts (`src/cache/manager.rs:108-118`, `src/cache/clean.rs:91`, `src/cache/config.rs:11`). Recorded responses served by a local replay server fit BioMCP better, and the repository already has most of the pieces: 72 source clients, 78 `BIOMCP_*_BASE`-style override variables, 9.5 MB of recorded provider responses under `testdata/sources`, and fixture servers that serve them.
9. mustmatch carries the spec lane: 592 bash blocks and 713 `mustmatch` assertions. 506 assertions are `mustmatch like` substring checks on human output, 128 are `jq -e ... | mustmatch 'true'` boolean checks that report only "expected true" when they fail, and 91 are named `expect=` blocks that compare JSON structurally. The median block is 3 lines, but 22 blocks exceed 40 lines and one is 265 lines (`spec/entity/drug.md`). The runner around mustmatch (`scripts/run-specs.sh`, 25 KB of bash, plus 60 fixture scripts and 5 Python test modules that test the runner and its fixtures) is where the complexity lives, not in mustmatch itself.
10. Coverage, measured with `cargo llvm-cov` on the build host (inline test modules and test files excluded): the outside-in tests alone, meaning the Rust integration tests, the Python lane and the spec pages, all driving the real binary, reach 65% of the production lines in `src/` (70,333 of 108,084); the unit tests alone reach 74%; both together 84%. Three quarters (74%) of the lines the unit tests cover, the outside-in suite covers too. 20,591 lines (19%) only unit tests reach, 11,040 (10%) only the outside-in suite reaches, and 17,160 (16%) nothing reaches. The outside-in suite never touches 34 production files (5,600 lines): the benchmark and search-all commands, update and install, local health checks, and nine source clients. 75 files, holding 19,159 unit-covered lines, are already covered at 90% or better by the outside-in suite; their unit tests are the first to go.

Recommendation, in one paragraph: spend 0.9.3 first on the build (delete `build.rs`, one profile for all routine gates, incremental compilation in the edit loop, no release build in routine CI), because every other step runs through the build dozens of times a day. Then take the three slow files out of the Python lane's critical path. Then replace the Python process checks and the ratchet inventories with a handful of compiler lints and delete the tests of the checkers. Then build one outside-in golden suite: the real binary, a local replay server fed by recorded provider responses, and JSON and Markdown outputs diffed against committed files. Then delete the unit tests that the golden suite and the spec lane already reach, using the coverage intersection below as the evidence. Keep mustmatch for the reader-facing spec pages, but stop writing JSON comparisons in bash: move those into golden files and shrink the runner. The ordered plan with payoffs and proofs is at the end.

## Measurements

The host's cargo config sets `incremental = false` and `debug = "line-tables-only"` for the dev profile. A first pass of these measurements was discarded because two copies of the measuring script ran at once and contended for the build lock; every number below comes from a second pass with one process, except the cold dev build, whose timings report shows an uncontended run.

Where the cold build's 257.8 s go (from the cargo `--timings` report of the first row): the 458 dependency units take 391.5 s of CPU but run four wide and finish by about 100 s of wall time; the `biomcp-cli` lib then compiles in 91.8 s and the lib test unit in 157.0 s, in parallel, starting at about 100 s; the lib test unit alone is the critical path, finishing at 257.7 s. The 26 integration test binaries, the two bins and the example compile and link in 0.1 to 7.7 s each (about 30 s of CPU in total, overlapped with the lib test). The largest dependency units are the `zstd-sys` build script (21.3 s), `rmcp` (19.6 s), `kuva` (15.0 s) and the `ring` build script (11.3 s). So the cost of an edit is the crate itself, and inside the crate it is the test code: the lib test unit takes 1.7 times as long as the lib.

The build script row is the costliest surprise. The repository has a `build.rs` that does nothing (`fn main() {}`); its two former jobs, proto generation and the git identity stamp, left in tickets 0936 and 0970 (`git log --oneline -- build.rs`). A build script that prints no `rerun-if-changed` line makes cargo rerun it whenever any file in the package changes, and cargo decides that by scanning every file the package would publish: tracked files plus untracked files that `.gitignore` does not cover, minus the `exclude` list in Cargo.toml:13-24. When the script reruns, the lib that depends on it recompiles, and every binary after it. The cargo log from the spec-profile build names the mechanism: `dirty: PrecalculatedComponentsChanged { old: "... (.study/A7.log)", new: "... (src/render/markdown/gene.rs)" }` on `build-script-build`, then `dirty: UnitDependencyInfoChanged` on `biomcp_cli` and on `biomcp`. In practice, editing a spec page, a Python test, a workflow file, a page under `docs/`, or `tools/rust-source-size-inventory.json` triggers the same 157 s dev recompile and 253 s spec recompile as editing Rust, in every checkout and in CI; `testdata/`, `sdlc/`, `.cache/` and `target/` do not, because they are excluded or ignored. Deleting `build.rs` removes the scan; rustc's own dependency tracking then limits rebuilds to the Rust files and the files they include (`include_str!` of fixtures under `testdata/`, `spec/fixtures/gtr` and `tests/fixtures/article`, all from test modules).

The names say what they wait for: cache ages, crash recovery across subprocesses, unreachable providers, deadlines. `sdlc/issues/2026-09-24-tests-wait-on-the-wall-clock.md` records the pattern and `tools/check-test-wait-ratchet.py` caps it at 46 markers. With four threads the suite runs in 149 s. Deleting fast unit tests shortens the compile, not this run; the run shortens when the slow eighty stop waiting on the clock.

Where the Python time goes (`--durations=80` from the stand-alone run; `--dist loadfile` sends every test of one file to the same worker, so the slowest file is the lane's floor): `tests/test_source_package_boundary.py::test_verified_source_package_is_zero_coupled_and_compiles_offline` takes 426 s to run `cargo package` and then `cargo check --locked --offline` of the packaged crate in a fresh target directory, a cold check of all 488 packages on every `make test` (`tests/test_source_package_boundary.py:104-140`). `tests/test_ctgov_trial_search_detail_reuse.py::test_combined_geo_and_eligibility_filters_fetch_one_detail_projection` takes 381 s for one `search trial` command against the intervention-alias fixture, while the file's other three tests take 7 s together. What it waits on, traced on the build host: the command makes two requests to the fixture (one search, one detail fetch) and spends the rest of the time inside the HTTP cache's start-up clean, reading the index of the developer's own cache at `~/.cache/biomcp/http`, because the test runs the binary without `BIOMCP_CACHE_DIR` and the fixture's `BIOMCP_CACHE_MODE=off` does not skip the clean (`src/sources/mod.rs:1226-1232, 1266-1274`; `src/cache/manager.rs:108-118`). During the run the binary's `biomcp-cli-exec` thread sat in uninterruptible disk wait with an index file under `~/.cache/biomcp/http/index-v5/` open and the maintenance lock held, reading 24 MB in 58,600 small reads over five minutes; that cache held 19,335 index files on the host's 5,400 rpm laptop disk. Run alone cold, the test took 304 s; run again at once, with the index in the page cache, the same command took 1.2 s. So the 381 s is a property of the host's cache and disk, not of the test, which is also why CI, with an empty cache, does not show it. Twenty-two Python test files run the binary this way, against whatever cache the developer has (`grep -L 'BIOMCP_CACHE_DIR\|XDG_CACHE_HOME\|biomcp-ci' $(grep -l BIOMCP_BIN tests/*.py tests/surface/*.py)`); the spec pages go through `tools/biomcp-ci`, which points the cache at `.cache/biomcp-specs`, and do not pay it. One more observation from the same trace: `spec/fixtures/fixture-supervisor.py` spun at 100% of one core for the whole test (1 voluntary against 3,609 involuntary context switches), which its `wait_for_owner_or_child` loop explains if the owner's pidfd is unavailable (`spec/fixtures/fixture-supervisor.py:135-150`); I did not trace why it was unavailable here and not under the spec runner, where the same supervisors idled at 0.1%. `tests/test_quality_ratchet_contract.py` sums to 427 s across its 54 tests, 175 s of it in `test_wrapper_writes_summary_artifacts_for_pass_fixture`, which runs the whole ratchet wrapper over the repository, and 85 s in `test_dead_code_allowance_audit_passes_for_repo` (`tests/test_quality_ratchet_contract.py:432-438`); eighteen more tests in that file take 5 to 54 s each. `tests/test_author_surface_docs.py` (210 s) and `tests/test_output_footprint_benchmark.py` (60 s) hit a 60 s timeout in the stand-alone run because of the temporary-directory path I set; run again by themselves with `make test`'s settings they took 33 s together against the `spec` binary (13.3 s for the token-count benchmark, 4.4 s for the slowest author test) and 75 s against the unoptimized dev binary (33.8 s and 12.4 s), all passing. Everything else in the lane sums to a few minutes spread across four workers. Eleven call sites in eight Python files run `cargo` (`grep '"cargo",' tests/`); two compile the real crate (the source-package test above, and `tests/test_short_unix_socket_contract.py:19-31`, which runs one lib test through `cargo test` and recompiles the lib test binary whenever the shared target directory is not fresh in that form; that test took 193 s in one lane run where the binary was stale), three build toy crates, the rest use fake `cargo` scripts.

### Coverage

Method: `cargo llvm-cov` 0.9.1 instruments the dev build (`cargo llvm-cov show-env` sets the compiler flags; `LLVM_PROFILE_FILE` with `%8m` pools the profiles). Three outside-in runs wrote profiles against the instrumented binary and MCP example: the Rust integration tests (`cargo nextest run -E 'kind(test)'`, 135 tests), the Python lane (`pytest tests/ -n 4 --dist loadfile` with `BIOMCP_BIN` pointing at the instrumented binary, 1,249 tests) and the routine spec lane (`scripts/run-specs.sh spec` with a hand-written `.cache/spec-artifacts.env` naming the instrumented binary and example, so the pages ran through `tools/biomcp-ci` and through `biomcp` on `PATH` as usual; 688 blocks, all passed). Under instrumentation three integration tests in `rmcp_client_contract` (one failed, two hit the 240 s timeout) and five Python tests (four in `tests/test_author_surface_docs.py`, one in `tests/test_output_footprint_benchmark.py`, all on 60 s limits) did not pass, so the outside-in figures undercount those paths a little. Those profiles were reported together as "outside-in" and set aside; the unit tests (`cargo nextest run -E 'kind(lib) | kind(bin)'`, 4,070 tests, all passed) wrote a second set, reported as "unit"; the union is both sets together. Line coverage comes from the lcov exports. Test code is removed by path (`tests/`, `tests.rs`, `*_tests.rs`, `tests_*.rs`, `test_support`, `generated/`) and inline `#[cfg(test)]` items are removed by line span, found by scanning the source at the studied commit (268 production files hold one, 35,247 lines in all, 25,626 of them instrumented); "production lines" below means the 108,084 instrumented lines that remain. Set arithmetic on the per-line hit counts gives the intersection, which no single report prints. The span scan is a brace-matching approximation, so treat the figures as accurate to about a point. `cargo llvm-cov`'s own summaries, which cannot remove inline test modules, read 52.4%, 78.3% and 86.2% of lines for the three sets.

## Build

What one ticket compiles today, from the Makefile and the workflow:

- `make lint` runs `cargo clippy --no-default-features -- -D warnings` through the identity wrapper (`bin/lint:95`), which compiles the dependency graph in check mode.
- `make test` first builds the `spec` profile binary and example for the Python lane (`SPEC_BUILD`, Makefile:23, called from `prepare-test-contracts` at line 44), then runs `cargo nextest archive --no-default-features` for the dev profile through the identity wrapper (Makefile:36), runs the archive offline, and then runs pytest and `mkdocs build --strict` (Makefile:51-52).
- `make spec` runs `scripts/prepare-spec-artifacts.py`, which builds the `spec` profile again (a freshness check when nothing changed), copies the binary and example into `.cache/spec-artifacts/`, and captures `cargo tree` and `cargo metadata` (`scripts/prepare-spec-artifacts.py:150-203`).
- `make verify`, the release gate, and CI's release-panic job build the release profile (Makefile:112-113, 69-72; `ci.yml:225`).

So routine work compiles three codegen profiles of the same crate. The `spec` profile exists only to run the spec pages against a release-like binary (Cargo.toml:160-163 explains the opt-level choice), yet nothing in the routine spec pages needs it: `spec/surface/build-profile.md` checks the feature graph through `cargo tree` output, not the binary's optimization level, and the pages run under the `release-gate` target against the real release binary anyway (Makefile:72). The dev test build already produces a `biomcp` binary that the integration tests use through `CARGO_BIN_EXE_biomcp`. Running the spec pages and the Python lane against that binary removes one whole profile from every ticket, and both lanes pass against it (measured on the build host): `make spec SPEC_PROFILE=dev` ran all 695 block runs green in 789 s, of which 76 s was the artifact preparation's own recompile of the crate (the stray files my coverage run left in the clone had tripped the build script scan), so the pages themselves took 713 s against 675 to 684 s with the `spec` binary; the Python lane against `target/debug/biomcp` passed 1,247 of 1,249 tests in 472 s, the same wall time as with the `spec` binary, and the two failures were `cargo package` counting a stray profiling file my coverage run had left in the clone, not the binary. The unoptimized binary is slower on heavy commands, about 2.5 to 3 times on the token-count benchmark and the article detail tests (13.3 s against 33.8 s, 4.4 s against 12.4 s), which both lanes absorb because their floors are elsewhere. The one behavior that differs between profiles is `debug_assertions`; `scripts/run-specs.sh:338-345` documents one place that cares (the GenCC fixture-override gate), and that gate becomes simpler, not harder, under a dev binary.

The build script comes first because it is one deletion. With it gone, a touched spec page or Python test no longer costs 157 s plus 253 s of Rust compile, and a developer who runs `make spec` after editing only pages gets the pages, not a build.

Incremental compilation is off on the build host by a deliberate choice recorded in its cargo config (the comment there cites a 2026-09-22 measurement that lean settings cut a fresh build from 833 s to 296 s and the next ticket's build from 374 s to 145 s). That choice trades the fresh-build size for the edit loop. The measurements above show what the edit loop pays: 157 to 188 s per touched file with incremental off, 67 to 144 s for a warm incremental rebuild of the whole test archive, and 55 s for a touch followed by one targeted test group (47 s compile, 8 s run). The two goals are compatible: keep `incremental = false` for the gates, set `CARGO_INCREMENTAL=1` for the developer's targeted `cargo nextest run -E 'test(...)'` loop that AGENTS.md:46-50 prescribes. Note that `cargo build --all-targets`, `cargo nextest run` and `cargo nextest archive` share one set of artifacts (the table's no-op rows), so a developer loses nothing by mixing them; what costs a rebuild is toggling `CARGO_INCREMENTAL`, which changes the fingerprint, so the setting has to be the same for the whole loop.

The crate's own test code is the other half of the compile. Test-only files under `src/` hold 93,601 lines, and 268 production files carry inline `#[cfg(test)]` items (35,247 lines, by a brace-matching scan of the source). All of it compiles into one lib test binary. Deleting tests, as the test-strategy section proposes, directly shortens the build, not only the run.

Linking: nextest archives 30 executables for the routine lane. Each of the 26 files under `tests/` links the full lib and its dependencies on its own, but the timings report shows this is cheap: 0.1 to 7.7 s per binary, about 30 s of CPU in all, overlapped with the lib test compile. Merging them would tidy the tree but would not speed up the build; the lib test unit is what to shrink. Seven of the 26 (`article_cli_tests_structure`, `article_transform_structure`, `benchmark_cli_structure`, `health_cli_structure`, `list_cli_structure`, `search_all_cli_structure`, `skill_cli_structure`) read source files and assert on module headers and file lists (`tests/list_cli_structure.rs:8-45`); they go for what they test, not for what they cost.

Build identity: `tools/with-build-identity` sets `BIOMCP_BUILD_GIT_SHA`, `BIOMCP_BUILD_VERSION` and `BIOMCP_BUILD_DATE` from git, including a `-dirty` suffix (`tools/with-build-identity:36-63`), and `src/main.rs:5-13` reads them with `option_env!`. Cargo tracks those reads, so the `biomcp` bin target recompiles whenever the values change: after every commit, when a tracked file changes, and whenever a developer alternates between the wrapper (`make test`, `make lint`) and bare `cargo nextest run` (AGENTS.md:49). Measured, this costs 2.1 s per toggle (the table's wrapper row; cargo logs `changed env "BIOMCP_BUILD_DATE"` for the bin only), so it is noise in the logs, not a cost worth a ticket of its own. If it is cleaned up anyway, set the identity only in the release workflow, where `release.yml:155` already calls the wrapper, and let dev builds carry the package version.

Dependencies: `Cargo.lock` lists 488 packages; the routine build compiles 434 of them (normal and build edges), 452 with dev-dependencies, 489 with all features (`cargo tree` counts). A target directory after one full routine build holds 7.1 GB (8.3 GB after the spec profile too), and the nextest archive is 316 MB. The routine feature set drops `tonic`, `prost`, `zstd` and the PNG chart backend (Cargo.toml:132-135). Dev-dependencies add `rexpect`, `rcgen`, `tokio-rustls`, `serial_test` and the in-tree `biomcp-mcp-contract-client` crate, which pulls `rmcp` with the client features (`crates/biomcp-mcp-contract-client/Cargo.toml`). None of this is unusual; the crate's own size is the cost, not the graph.

Toolchain notes: Rust 1.93.1 on x86_64 Linux uses `rust-lld` by default (inferred from the Rust 1.90 release notes; not measured here), so a linker switch would gain little. The host has no `sccache` or `mold` installed, and no `.cargo/config.toml` in the repository sets build options; `.config/nextest.toml` sets only the slow-test timeout.

## CI

The workflow runs eight jobs on every push to main and to ticket branches (`ci.yml:11`). Wall time is the longest job, canonical-gates, at 22 to 26 minutes; the other seven jobs run in parallel and add runner-minutes but not wall time. Inside canonical-gates the three gates run serially on one runner: lint about 1.5 minutes, `make test` 9 to 11 minutes, `make spec` 10.6 to 11.3 minutes. `make test` already built the `spec` profile on that runner (Makefile:34-36), so `make spec` is 11 minutes of pages, fixtures and the section-outcomes pytest module, the same 11 minutes the build host shows with nothing to compile. The rust-cache action restores the target directory between runs (inferred from the workflow; its key is not profile-specific), but every commit changes a file in the package, so the build script scan (Build section) recompiles the crate in both profiles on every run anyway.

Three things make CI slower than it needs to be:

1. The same build repeats across jobs. canonical-gates and stress-lane both run `cargo nextest archive --no-default-features` (Makefile:36, 138); release-panic and full-features each run a release build; windows-contracts runs its own check and three test targets. Each starts from its own restore of the rust-cache action.
2. release-panic spends 16.4 minutes to build a release binary and run one test, `rmcp_stdio_recovers_from_tool_panic` (`ci.yml:223-226`). The ticket that added it wanted the release-mode panic path proved (the comment at `ci.yml:198-202`). That proof belongs in the release workflow, which builds release binaries anyway (`release.yml:155`), or once a day, not on every push.
3. Everything runs on every push, including pushes to ticket branches that developers make after each fix (AGENTS.md:89 asks for a green branch run before merging, and one recent ticket's build record counted 12 `make test` runs, 3 `make spec`, 8 `make lint` and 27 targeted nextest runs in 4.8 hours, about 3 hours of it waiting on gates). 107 runs in one day at about 70 runner-minutes each is the result.

The fix follows from the build section. One build job produces the nextest archive and the binary once and uploads them as artifacts (or the three gates run as three parallel jobs with the same cache key, which the rust-cache action supports); lint, the Rust tests, the Python lane and the spec lane then run in parallel against those artifacts. With the spec profile gone, the spec job needs no compile at all. Target: a green run in about the time of the longest single lane, which today is `make test` at 9 to 11 minutes and which the test-strategy section shortens further. Proof: the Actions API job durations before and after, on the same commit range.

The repository-contracts job (pytest without the binary, 1.4 to 1.7 minutes) is the model for a cheap lane. The docs-only skip (`ci.yml:29-45`, `scripts/ci-classify-push.sh`) works and is worth keeping.

## Test strategy

What the suite proves today, by layer:

- The spec pages are the outside-in surface for the CLI and the MCP server. The routine lane runs 37 pages and about 955 `biomcp` invocations against local fixture servers with the network blocked (`tools/run-offline` wraps every gate in a `bwrap --unshare-net` sandbox, `tools/run-offline:46-62`). They assert on human output with `mustmatch like` and on JSON with `jq` predicates or `expect=` blocks.
- The Rust integration tests under `tests/` cover error contracts, the MCP client contract through the in-tree client crate (`tests/rmcp_client_contract.rs`, 23 tests), TLS trust, cache clearing, and a few CLI behaviors. Seven of the 26 files are source-text checks, not behavior tests.
- The Python tests mostly check the repository, not the product. By file name, 299 tests check the checkers (`tests/test_quality_ratchet_contract.py` alone has 54; `tests/test_capture_receipts.py` 43; `tests/test_small_rust_test_boundaries.py` asserts that specific strings appear in specific Rust test files), 227 check release and CI workflow files, 133 check documentation wording, and 127 check records and the changelog. 175 drive the binary or the MCP server. The classification is by file name and is approximate; the shape is not.
- The 4,031 Rust unit tests test the layers underneath. In `src/sources`, 322 "construction" tests check that a client builds the right URL or path segments (`src/sources/kegg/tests/construction.rs`) and 431 "parsing" tests feed recorded or synthetic payloads to parsers (`src/sources/kegg/tests/parsing.rs`). In `src/cli`, 144 tests parse argument vectors with `Cli::try_parse_from` and 83 tests render `--help` and assert on substrings (`src/cli/disease/tests.rs:21-38`), while 44 spec assertions also run `--help` on the built binary. `next_commands` output is asserted in 34 unit test files, 17 files under `tests/`, and 15 spec pages.

The same behavior is tested at several layers, which is the sediment pattern from the project's outside-in note (Ian Maurer, "Red, Green, Remove", https://www.imaurer.com/writing/red-green-remove-outside-in-tests/): a refactor that keeps behavior breaks tests at each layer, and the suite's cost grows with the layers rather than with the behaviors. The outside-in guidance says to test each behavior once on the surface that owns it, to keep edge-case tables for parsers, contract checks on what others depend on, and regressions, and to delete the rest with coverage as the evidence. The coverage section gives the evidence for BioMCP: 74% of the lines the unit tests cover, the outside-in suite covers too, and in 75 files the overlap is 90% or better.

Recommended shape for 0.9.3:

1. One golden outside-in suite. Each case is a real `biomcp` command (and the same command through the MCP tool where the surface differs), run against a local replay server, with its JSON and Markdown output committed as files and compared by diff. A `--update` switch regenerates the files; the diff is the review. The cases come from the spec pages' existing commands (about 955 invocations, most of which reduce to a few dozen distinct commands per entity). This is the test that makes an output-format refactor cheap: change the renderer, regenerate, read the diff, commit.
2. Keep the four kinds the guidance names, and name them: behavior cases (the golden suite and the reader-facing spec pages), edge-case tables (the parsing tests in `src/sources/*/tests/parsing.rs` that are tables, the variant input-form grammars, the eligibility and date parsers), contract checks (MCP schema and tool catalog, JSON error shape, release artifact contents, the public CLI surface), and regressions that failed before a fix.
3. Delete, with the coverage intersection as evidence: construction tests whose URL the replay server's request log already asserts; help-text and `try_parse_from` tests where a golden `--help` case exists; render tests that the golden Markdown files cover; the Python checks of checkers; the seven structure-check binaries; and the ticket-named test files once their claims have a behavior-named home.
4. Two suites, as the guidance says: the routine suite above, each case a few seconds, and a release suite with the live `make verify` lane, the all-features build, Windows, and the stress lane.

## Caching and fixtures

How the cache works, from the code:

- The shared client is built once per process (`src/sources/mod.rs:1517-1540`). Unless `--no-cache` is set, it wraps `reqwest` with provider rate limiting, the `http-cache` middleware in `CacheMode::Default`, retry, and a response-size limit (`src/sources/mod.rs:1341-1365`). The request carries `Cache-Control: max-stale=86400` by default (`src/sources/mod.rs:1320`), so a response without cache headers is reused for 24 hours.
- The store is `cacache` on disk under `<cache root>/http` behind `SizeAwareCacheManager` (`src/cache/manager.rs:73-81, 238`). The cache root comes from `BIOMCP_CACHE_DIR`, then `cache.toml`, then the platform cache directory (`src/cache/config.rs:84-104`, documented in `docs/reference/configuration.md:21-36`). Defaults: 10 GB, 24 hours, 10% free disk (`src/cache/config.rs:10-12`). Entries are keyed `method:uri` (the `http-cache` default) and stored as `bincode` of the response plus its cache policy (`src/cache/manager.rs:283-297`).
- `BIOMCP_CACHE_MODE=infinite` maps to `ForceCache` (serve any stored entry regardless of age, fetch on a miss) and `off` to `NoStore` (`src/sources/mod.rs:563-571`). The variable is read once per process (`src/sources/mod.rs:574-581`); tests use a scoped override instead (`src/sources/mod.rs:590-646`). `--no-cache` scopes a task-local flag that selects an uncached client (`src/sources/mod.rs:1227-1231`). Authenticated requests are never stored. Test builds point the default cache root at a per-process temp directory (`src/cache/config.rs:141-148`).
- On construction, the manager takes the maintenance lock and runs a clean with `max_age: None`, which resolves to the configured 24 hours (`src/cache/manager.rs:108-118`, `src/cache/clean.rs:91`), physically removing older entries. The documentation says the same (`docs/reference/configuration.md:38-41`). The clean snapshots the whole store first (`src/cache/planner.rs:56`), which means one read per index file; `BIOMCP_CACHE_MODE=off` does not skip it, only `--no-cache` does (`src/sources/mod.rs:1226-1232`). On the build host, whose cache holds 19,335 index files on a 5,400 rpm disk, that snapshot took about five minutes when the page cache was cold and about a second when it was warm (measured through the trial search test described under Test times). Every `biomcp` command a developer runs pays the same snapshot against their own cache (inferred from the code path; measured only through the test).

What this means for a pre-baked test cache: it would work only while the entries are under 24 hours old or `BIOMCP_CACHE_MAX_AGE` is raised for the test run; it would be a tree of hashed index files and binary blobs that nobody can review in a pull request; its format is owned by `http-cache` and `bincode` and changes when they do; and it needs the real provider URLs as keys, so every case first needs a live run to record. The spec lane already has a form of this: `tools/biomcp-ci` points the cache at `.cache/biomcp-specs` and switches to `infinite` when `BIOMCP_SPEC_CACHE_HIT=1` (`tools/biomcp-ci:5-13, 37-39`); the local checkout's copy is 132 MB in 11,010 files. `spec/README-timings.md` describes a CI step that restores that directory, but the current `ci.yml` has no such step (inferred by reading the workflow), so the routine pages rely on the fixture servers instead. On the build host, `.cache/biomcp-specs` held no files after two `make spec` runs (measured): the runner sources the shared provider fixture's environment for the pool pages, and that environment sets `BIOMCP_CACHE_MODE=off` (`scripts/run-specs.sh:271`, `spec/fixtures/setup-provider-contract-spec-fixture.sh`; nine of the 57 fixture scripts set it). So the routine spec lane neither reads nor writes the HTTP cache today, and its 11 minutes are not a cache problem.

Two more facts about the client matter for fixture-backed tests. First, every start of the cached client runs a cache clean over the whole store when no other process holds the maintenance lock (`src/cache/manager.rs:108-118`); with the cache off (`NoStore`) the fixture-backed pages skip that cost. Second, the provider rate limiter keys its pacing on the configured base URL, not on the real provider's host: `policy()` builds each prefix from the `BIOMCP_*_BASE` override (`src/sources/rate_limit.rs:285-296`), so a fixture server standing in for PubTator is paced at PubTator's interval (334 ms without an NCBI key), one standing in for LitSense or NIH RePORTER at 1 s, for Semantic Scholar at 2 s without a key, and every other origin at 100 ms (`src/sources/rate_limit.rs:96-190`). Only requests to the one origin named in `BIOMCP_TEST_UNPACED_ORIGIN` skip the wait (`src/sources/rate_limit.rs:28-30, 226-233`); among the spec pages only `spec/entity/gene.md` sets it, and eight article fixture scripts export it. The limiter is per process, so a single command pays only when it asks the same provider more than once, which the article and trial searches do.

What the repository already has for recorded responses:

- 72 source client modules under `src/sources`, and 78 base-URL override variables (`BIOMCP_MYGENE_BASE`, `BIOMCP_CTGOV_BASE`, `BIOMCP_PUBMED_BASE`, and so on). Every client except three reads one; the three (`cbioportal_study`, `ddinter`, `clingen_cspec`) use a local data directory or a fixture-origin variable instead (inferred from a grep of the module files).
- 363 recorded or authored provider payloads under `testdata/sources` (9.5 MB) with a provenance manifest (`testdata/sources/capture-receipts.json`).
- Fixture servers written in Python inside the spec fixture scripts that serve those payloads by URL pattern and log every request (`spec/fixtures/setup-provider-contract-spec-fixture.sh:68-80`). Spec pages then assert on the request log to prove what the client asked for (`spec/entity/gene.md:63-98`).

The missing piece is one replay server instead of twenty fixture scripts: a single process that maps `method:path?query` to a recorded response file, records a miss when a `--record` flag allows live traffic, and serves everything else from disk, with the offline sandbox refusing any other network. Point every `BIOMCP_*_BASE` at it with one helper. The golden suite and the spec pages both run against it. Recording is a one-time live call per new case, so provider rate limits stop mattering to routine tests; the live `make verify` lane keeps proving the real providers at release time. Compared with a pre-baked HTTP cache, the recordings are plain files that reviewers can read and that survive cache-format and age changes.

## mustmatch

What it is: a standalone binary (`mustmatch 0.1.0`, installed with `uv tool install` in CI, `ci.yml:107`) that compares stdin with an expected string (`mustmatch [not] [like] EXPECTED`) and runs the bash blocks of Markdown files as tests (`mustmatch test --lang bash --timeout 180`). `scripts/run-specs.sh` runs the pages in three groups: a serial article group that shares one fixture server and request log, the section-outcomes page with its own fixture, and a pool of four parallel workers for the rest (`scripts/run-specs.sh:132-147, 394-470`).

How much depends on it: all 592 bash blocks in 52 pages, which is the only outside-in coverage of most entity surfaces. The routine lane alone is 37 pages, 524 blocks, 713 assertions, and about 955 binary invocations.

Does it serve its purpose? Partly. The pages are readable specifications, the `like` matches on human output are short and fail with a useful diff, and the `expect=` blocks read well (`spec/entity/author.md:15-27`). Three things work against it:

1. JSON comparison is done in bash. 128 assertions are `jq -e '<predicate>' | mustmatch 'true'`; a failure prints "expected true, got false" and nothing about which field differed. Writers compensate with long predicates (`spec/entity/gene.md:30-36`) and the blocks grow: the four largest blocks are 265, 176, 150 and 108 lines, and 22 blocks exceed 40 lines. A 265-line bash block is a test program in a Markdown file, with none of a test program's tools.
2. Request-log accounting is done by hand in each page (`spec/entity/gene.md:60-98` counts `grep` hits before and after each call), and the runner namespaces request logs per worker to keep that accounting correct (`scripts/run-specs.sh:222-283`). That is harness logic written in the specification.
3. The machinery around the pages has grown into its own project: a 25 KB runner with locks, orphan reaping and ownership markers; 60 fixture scripts; `spec/fixtures/fixture-supervisor.py`; and Python tests that test the runner and fixtures (`tests/test_article_spec_fixture_lifecycle.py` 21 tests, `tests/surface/test_parallel_isolation_contract.py` 41 tests, `tests/test_routine_fixture_recovery.py` 9, plus three more lifecycle modules). The lifecycle tests copy the workspace and run the runner inside it (27 s and 16 s for the two largest modules in the stand-alone Python run). This is the proof spiral: tools that check the checks.

Recommendation: keep mustmatch, do not extend it, and move the weight off it. Keep the pages that a reader learns from, with short `like` assertions and `expect=` blocks. Move every JSON comparison into the golden suite, where the expected JSON is a file and the failure is a diff. Delete the request-log arithmetic from the pages once the replay server asserts requests in the golden cases. Replace the fixture scripts with the one replay server, then delete the runner's lifecycle and parallel-isolation tests with them. If after that the pages still need a feature (a JSON diff, a per-block budget report), add it to mustmatch then; today the problem is not mustmatch's features.

Measure the lane after the change by the numbers that matter: wall time for `make spec` (675 to 684 s today with nothing to compile), lines of harness (runner plus fixtures), and the number of bash blocks over 40 lines (22 today). Where the 11 minutes go (a run with a timestamp on every output line): fixture standup 4 s; the serial article group (five pages, 213 blocks, one shared fixture) 155 s; the four-worker pool over 27 pages 321 s, with `variant.md` (111 blocks), `drug.md`, `gene.md` and the protein-change page as the long tails; then `section-outcomes.md` alone, 15 blocks in 164 s; the 41-test pytest module 2 s; the two static pages under a second. About 650 s in all, of which only the pool runs four wide. The same run also showed the build script scan at work: `make prepare-spec` recompiled the spec-profile crate for 4 m 49 s because an untracked directory had appeared in the clone since the last build.

Where a slow page's time goes, traced on `spec/entity/section-outcomes.md` run by itself under `mustmatch -v` with a timestamp on every line: 126 s for the page, 120 s of it in the two blocks of the heading "Drug interaction failure preserves a multi-section card" (`spec/entity/section-outcomes.md:97-136` and `192-223`, 55 s and 65 s). Those blocks run the binary 15 times against fixture drugs whose names end in `-openfda-fail`, and each such command takes 4.1 s where a healthy command on the same page takes 0.13 to 0.24 s: the fixture answers with a failure, and the client's retry middleware tries three more times, sleeping about 1.5 s between attempts (`src/sources/mod.rs:1330-1356`; the binary logged `Retry attempt #1. Sleeping 1.53s` and `#2 ... 1.62s`). The spec lane is full of fixtures that simulate failure, timeouts and deadlines on purpose, so this is where much of its idle time comes from: real back-off sleeps against fake failures. The article group has the same shape with its deadline and federated-timeout fixtures. The two blocks that failed in this stand-alone run needed the runner's MCP example environment, which my direct invocation did not provide; the timings of the other thirteen stand.

## Dead code and duplicate tests

Dead code: the compiler already finds it; the repository then permits it. There are 123 `#[allow(dead_code)]` and 63 `#[allow(unused_imports)]` markers in `src/`, 20 of the import allowances on the cache module's re-exports alone (`src/cache/mod.rs:58-97`). `tools/dead-code-exceptions.json` records 124 reviewed exceptions with owner, reason and removal condition; 82 sit in `src/sources` and 80 reasons mention a fixture or a test ("`AuthPostJson` models authenticated JSON health probes in the catalog", "exercised by binary dispatch or CLI contracts"). Items that exist for tests are the dead code the outside-in guidance means. Coverage adds the other measure: 17,160 production lines (16%) run under no test at all, led by `src/entities/gene.rs` (735 of 2,295 lines), `src/entities/variant/gwas.rs` (340 of 489), `src/entities/adverse_event.rs` (338 of 1,241), `src/cli/benchmark/run/execute.rs` (313 of 322), `src/entities/disease/associations.rs` (305 of 541) and `src/cli/system/dispatch.rs` (303 of 502); the full list is in the coverage section. A line no test reaches is dead or untested, and either way it is the first place to look.

Duplicate tests, with evidence:

- Help text: 83 unit tests render `--help` in-process and assert substrings; 44 spec assertions run `--help` on the binary. One golden `--help` case per command replaces both.
- Argument parsing: 144 `Cli::try_parse_from` tests. A golden case through the binary covers the accepted forms; the rejection messages belong in one edge-case table.
- `next_commands`: asserted in 34 unit test files, 17 files under `tests/`, and 15 spec pages.
- Source clients: 322 construction tests check URLs that the fixture servers' request logs already record (`spec/entity/gene.md:60-98` asserts the exact MyGene query string). A replay server that fails on an unrecorded request makes the URL assertion free.
- Structure checks: seven Rust integration binaries and several Python modules assert on source text (`tests/list_cli_structure.rs`, `tests/test_small_rust_test_boundaries.py`, `tests/test_central_test_support_helpers.py`). They guard conventions, not behavior; the ones worth keeping become clippy configuration or a 20-line script, not linked test binaries.
- Ratchets: `tools/rust-source-size-inventory.json` (file size floors with per-ticket authorized increases) changed in 90 commits since 2026-10-01; `tools/test-wait-inventory.json`, `tools/zero-coupling-historical.json` and the dead-code inventory are the same pattern. 36 of 676 commits in that period changed only a `tools/*.json` file. In the timed `make lint` run the ratchet wrapper alone took 70 s of 164 s, more than clippy's 56 s. Clippy's `too_many_lines` and `disallowed_methods` lints enforce the two conventions that matter (file growth and clock-based waits, the latter already proposed in `sdlc/issues/2026-09-29-replace-text-scanning-checks-with-compiler-tools.md`) inside the compiler, with no inventory to re-stamp.

Useless tests: `tests/test_quality_ratchet_contract.py` (54 tests) and `tests/test_capture_receipts.py` (43) test the checkers; `tests/test_test_wait_ratchet_check.py` (20) tests the ratchet; the fixture lifecycle modules test the fixture scripts. When the checkers and scripts go, these go with them.

## The 0.9.3 plan, in order

Each step names the payoff and the proof. The order puts the build first because every later step runs through it.

1. Delete `build.rs`. Nothing reads it, and with it gone cargo stops rescanning the package and recompiling the crate after every non-Rust edit. Payoff: a touched spec page, Python test, workflow or inventory file no longer costs 157 s of dev build plus 253 s of spec build; measured on the build host, the same touches went from 175 s to 2.7 s once the file was gone. Proof: repeat the two build-table rows after the change, and watch a CI run that touches only a spec page restore the crate from cache without compiling.
2. One build per ticket. Run the spec lane and the Python lane against the dev test build's binary; drop the `spec` profile from routine gates and keep it (or the release profile) for `make release-gate` only. Set `CARGO_INCREMENTAL=1` in the documented targeted-test loop and keep it off for the gates. Both lanes already pass against the dev binary (measured; see Build), at a cost of about 5% on the spec lane's wall time and none on the Python lane's. Payoff: 253 s of spec-profile compile gone from every `make test` and `make spec` after a Rust edit; the touch-and-test loop drops from about three minutes to about one; a developer's `make spec` after a page edit compiles nothing. Proof: time `make test` and `make spec` on the build host before and after; the number of `Compiling biomcp-cli` lines in a ticket's cargo logs.
3. Take the three slow files off the Python lane's critical path. Move `test_verified_source_package_is_zero_coupled_and_compiles_offline` to the release gate, where a cold `cargo check` of the packaged source belongs, and run the one lib test behind `tests/test_short_unix_socket_contract.py` from the nextest archive instead of through `cargo test`; give every Python test that runs the binary an empty `BIOMCP_CACHE_DIR` under the test's temporary directory (one line in a shared pytest fixture), which removes the 381 s from `test_combined_geo_and_eligibility_filters_fetch_one_detail_projection` and stops 22 test files from reading and cleaning the developer's own cache; separately, make the start-up clean cheap for users with large caches on slow disks (skip it when the cache mode is `off`, run it at most once a day behind a marker file, or leave it to `biomcp cache clean`); run the ratchet's self-tests against a small fixture repository instead of the whole checkout, or delete them with the ratchet in step 5. Payoff: the Python lane from 473 s to about its remainder, on the order of two minutes (inferred from the per-file sums), and `make test` from 635 s to about 300 s before any other change. Proof: `pytest --durations=20` per-file sums and the `make test` wall time.
4. CI as one build and parallel lanes. One job builds and uploads the archive and binary; lint, Rust tests, Python lane and spec lane run in parallel from it; stress-lane reuses the archive; release-panic moves to the release workflow or a daily schedule; full-features and windows stay but run on main only. Payoff: wall time from 22 to 28 minutes to about the longest lane; runner-minutes from about 70 to about 30 per run (inferred from the job table). Proof: Actions API durations for ten runs before and after.
5. Replace the process checks with compiler lints. Turn on `clippy::too_many_lines` with the current threshold and `disallowed_methods` for the sleep and clock calls; delete the four inventory files, `tools/check-quality-ratchet.py`'s audits that only read those inventories, `tools/check-test-wait-ratchet.py`, the structure tests, and the Python tests of the checkers (about 300 tests by the file-name count, 427 s of the Python lane in one file). Keep the capture-receipt manifest as data without its 54 KB checker, or fold it into the replay server's recording step. Payoff: `make lint` loses the ratchet wrapper's 70 s (of 164 s in the timed run) and the Python lane its 427 s file, and re-stamp commits stop (36 of 676 since 2026-10-01). Proof: `make lint` and pytest wall time; zero commits whose only change is a `tools/*.json` file over the next release.
6. The replay server and the golden suite. One replay server over `testdata/sources` with a request log and a record mode; a `BIOMCP_REPLAY_BASE`-style helper that sets every `BIOMCP_*_BASE`; a golden test that runs each command and diffs JSON and Markdown against committed files, with `--update`. Seed it from the spec pages' commands, one entity at a time, starting with gene, variant, trial, article and drug. Payoff: output-format refactors become regenerate, read the diff, commit; live rate limits leave the routine gates. Proof: coverage of `src/render` and `src/cli` from the golden suite alone, against today's 70% and 48% from the whole outside-in suite; a renderer change landed with only golden-file updates.
7. Delete unit tests the outside-in suite reaches, and stop the slow ones waiting. Use the coverage intersection: for each production file, the share of its unit-covered lines that the outside-in suite also covers; delete the unit tests of files at or near 100% first (help, parse, construction, render), keep parser edge tables and regressions, and write the missing golden case before deleting any sole test of a behavior. Give the 81 tests that take a second or more (399 s of the 528 s of test time) an injected clock or a shorter deadline. Land in small batches. Payoff: the lib test binary compiles faster (test code is 44% of the crate and the lib test unit is the build's critical path at 157 s) and the run drops below its 149 s; refactors stop breaking tests of layers. Proof: production-line coverage of the union stays within a few points of today's 84% while the test count, the compile time of the lib test unit and the run time fall. Start with the 75 files where the outside-in suite already covers 90% or more of the unit-covered lines (19,159 lines), and add outside-in cases for the 34 files it never touches before deleting anything there.
8. Shrink the spec lane. First the cheap part: let a test environment variable (or the replay server's failure responses) turn the retry back-off to zero, so a simulated provider failure costs one attempt instead of 4 s of sleeping; the section-outcomes page alone drops from about two minutes to seconds, and the deadline fixtures in the article group should get the same treatment with an injected clock. Then move JSON assertions and request-log arithmetic into golden cases; cut every block over 40 lines; replace the fixture scripts with the replay server; delete the lifecycle and parallel-isolation tests with them; keep the pages as reader-facing specifications with `like` and `expect=` assertions. Payoff: `make spec` from 11 minutes to a few, with no fixture standup, and the runner from 25 KB of bash to a loop over pages. Proof: `make spec` wall time, harness line count, count of blocks over 40 lines.

Testing strategy: mostly outside-in through the binary and the MCP server against a replay server, with golden JSON and Markdown; unit tests only for parser edge tables, security boundaries and regressions; no test waits on the wall clock. Build strategy: no build script, one dev build per ticket, incremental in the edit loop, release profiles only in the release gate and release workflow. mustmatch: keep, do not improve, shrink what runs through it.

## What I could not measure

- The release workflow and `make verify`. Both call live providers and build the release profile; I did not run them. The Actions API gives the release workflow's past durations (26, 2, 59, 40 and 50 minutes for the last five successful runs; the most recent runs failed early), and CI's release-panic job gives the release build's cost on a hosted runner (16.4 minutes). Command for the build host: `tools/with-build-identity cargo build --release --locked` under `/usr/bin/time`.
- The all-features build (`make full-feature-check`) and the Windows job. CI shows 11.7 to 12.2 and 8.5 to 8.7 minutes; I did not repeat them locally.
- `make test` as a whole against a dev-profile binary. I ran the Python lane and the spec lane against it separately (both pass; see Build) but not the Makefile's own `test` target with the `spec` profile removed, which needs the Makefile change itself. Command after that change: `make test` and `make spec` under `/usr/bin/time`.
- A CI run with `build.rs` deleted, to confirm the rust-cache restore then leaves the crate fresh on a docs-or-spec-only push. The host measurement (2.7 s against 175 s) predicts it; a ticket branch with that one deletion and a spec-page edit proves it.
- Coverage from the spec pages alone versus the Python lane alone versus the Rust integration tests alone. I pooled the three outside-in runs into one profile set to keep the host time down; three separate sets would say which surface earns its keep. Command: the same `cargo llvm-cov` sequence with `cargo llvm-cov report --lcov` after each run and the profiles moved aside between runs.
- Build and test times on other machines. All build-host numbers here come from one 4-core, 14 GB machine; a laptop with fewer cores or a slower disk will be slower in proportion to the CPU seconds given beside each wall time.
- The CI bill in money or exact runner-hours. I counted runs (`gh run list --limit 200`) and read two runs' job durations; the product is an estimate.

Measurement notes for anyone repeating this: build one thing at a time on a shared host and check `pgrep -x cargo` first; keep logs outside the clone or in an ignored directory, because any untracked file inside it is scanned by the build script and also fails the zero-coupling lint; set `TMPDIR` to a short path when running the Python lane by hand; and when handing the spec runner a binary of your own, put it in a directory of its own under the name `biomcp`, because the runner puts that directory on `PATH` (`scripts/run-specs.sh:745`) and the pages that call `biomcp` by bare name will otherwise run whatever `biomcp` the host has installed (my first coverage run did exactly that; 178 blocks failed against an unrelated binary and the run was repeated). For coverage, remove inline `#[cfg(test)]` modules by line span before computing shares; counted as production code they add 25,626 instrumented lines that only the unit build can reach and move the headline figures by ten points or more.
