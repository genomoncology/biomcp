# Full-disk cache review

The bounded experiment confirmed that provider answers survive actual full-filesystem cache-write failures and no staging files leak. It found a defect: successful explicit cache cleanup does not refresh the saved byte total after deleting content.

- Source: `9593a032b534b6252b1133c657c1088f7c5e908f`; copied executable version `0.9.4-dev+g9593a032`, SHA-256 `c51deb4fe552a89d038afd6f1379aa87cc921f313fa828536959a5a12bd9809c`.
- Execution: initial build job `2202/1792350122961-45412`, exit 1 after 3.401 seconds; approved corrected attempt `2202/1792350179375-53977`, exit 1 after 3.311 seconds. Both used the same copied executable from the passing main check; neither rebuilt it.
- Isolation: one ordinary-user 32 MiB HFS+ image; generated loopback-only gene-provider replies; separate home, configuration, temporary files, and cache. No external provider or production cache was used.
- Commands: `hdiutil create -size 32m -fs HFS+ -volname biomcp2202 -type UDIF -nospotlight "$IMAGE"`; `hdiutil attach -nobrowse -mountpoint "$MOUNT" -plist "$IMAGE"`; copied CLI `--json search gene BRAFcontrol --limit 1`, repeated once, then `--json search gene BRAFpressure --limit 1`; in the corrected attempt, `--json cache clean --max-size 1B`, `--json search gene BRAFwhilefull --limit 1`, then another `--json cache clean --max-size 1B` after deleting filler; `hdiutil detach "$MOUNT"`.
- Control: the cache held 2,098,613 content bytes, its marker agreed, no staging files existed, and the repeated request used the cached answer without another provider request.
- Pressure: a bounded filler on the attached filesystem reached kernel errno 28 after 30,605,312 bytes. Releasing 128 KiB before the next approximately 2 MiB reply caused the CLI to report `io_kind=Some(StorageFull) os_code=None`. The command returned 0 with the provider answer.
- Initial-attempt limitation: the script expected numeric `os_code=28`, so it stopped despite the storage-full diagnostic. This diagnostic assertion established no product failure. The corrected attempt accepted actual filler errno 28 together with the CLI storage-full diagnostic and captured cache state before assertions.
- Corrected attempt: after the failed write, content remained 2,098,613 bytes, the marker conservatively counted 4,197,228, and no staging files remained. Filling the filesystem again and running cleanup succeeded with `errors: []`, removed one entry, and freed all 2,098,613 content bytes; the marker stayed unchanged. The following pressured provider request returned its answer with exit 0 and `os_code=Some(28)`.
- Defect: after releasing filler, another cleanup returned 0 with `errors: []`, content totaled zero, and no staging files remained, but the marker contained `v2 6295845`. Successful maintenance did not reconcile accounting. `src/cli/cache.rs::execute_clean` delegates deletion to `src/cache/clean.rs::execute_cache_clean`, and neither refreshes the totals marker afterward. The experiment stopped at this concrete discrepancy; the final post-recovery provider request did not run. Product code remains unchanged.
- Cleanup: both attempts detached their owned image successfully and removed it. Raw commands, replies, artifact identity, and the disposable scripts remain in experiment `774` and its `attempt2` subfolder, owned by `biomcp/2202`, until the finding is recorded and accepted. No image remains attached.

Reuse the qualified short-process and concurrent size-accounting checks from 2195 and bounded eviction checks from 2206. Failed writes may conservatively overcount until maintenance; this review introduces no immediate-exactness requirement. The approved review scope specifically requires accounting recovery after removing filler and successful cleanup. Startup cleanup and automatic eviction already reconcile the saved total, but explicit cleanup omits that step. The observed defect is stale accounting after successful explicit maintenance; the experiment does not demonstrate a size-limit breach or provider-answer loss.
